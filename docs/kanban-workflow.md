# Доска задач и ритм работы

Задачи ведутся в GitHub: issue в репозитории `tuman-langs-mobile` (приложение, дизайн, контент, тесты) или `tuman-langs-backend` (сервер) + общая доска «Туман — MVP». EduFlow остаётся системой, которую смотрят преподаватели, поэтому раз в неделю прогресс с доски переносится туда (скриптом `tools/eduflow-sync`, он же запускается в GitHub Actions).

## Колонки доски

| Колонка | Что значит |
|---|---|
| Бэклог | Задача описана, но не запланирована на неделю |
| На неделю | Взята в план текущей недели, у неё есть ответственный и даты |
| В работе | Ответственный начал; есть ветка |
| На ревью | Открыт PR, ждёт проверки |
| Готово | PR влит, результат проверен по критерию задачи |

В EduFlow у доски три колонки: «Нужно сделать», «В процессе», «Готово». Соответствие: Бэклог и На неделю → «Нужно сделать»; В работе и На ревью → «В процессе»; Готово → «Готово».

## Поля задачи

- **Ответственный** — ровно один (assignee). Помощники перечисляются в описании.
- **Начало / Окончание** — обе даты обязательны: по дате начала руководитель видит, что работа пошла, а не началась за день до срока.
- **Этап ТЗ** — номер этапа из раздела 7 ТЗ (1–10).
- **Контрольная точка** — ближайшая из 26.10, 02.11, 09.11, 16.11, 23.11.
- **Результат** — что именно можно проверить: сборка APK с конкретной функцией, файл, ссылка на макет, протокол. Не «документ Word» и не «изучить».

## Метки

По ролям: `android-ui`, `android-algo`, `android-data`, `backend`, `design`, `content`, `qa`, `docs`.
По типу: `feature`, `bug`, `test`, `research` (у research-задачи всё равно должен быть проверяемый результат, например заметка в `docs/` или прототип).

## Ветки и PR

Ветка на задачу: `<тип>/<номер>-<кратко>` — `feature/`, `fix/`, `test/`, `docs/`, `content/`, `design/`. Например `feature/12-card-editor`. PR в `main` с `Closes #12` в описании: после слияния issue закрывается, карточка уходит в «Готово». Пошагово — `docs/onboarding.md`.

## Ритм недели

- **Понедельник** — у первокурсников в этот день свободное окно, общий созвон удобно ставить на него. Разбор прошлой недели, план на неделю, перенос задач в «На неделю».
- **Среда** — короткая проверка: что застряло, кому нужна помощь.
- **Воскресенье вечером** — каждый обновляет свои карточки и пишет итог в issue. Руководитель переносит прогресс в EduFlow до понедельничной контрольной точки.

## Критерии готовности (Definition of Done)

- Код в `main` через PR, ревью пройдено.
- Выполнен критерий из задачи, и он проверен (тестом, на устройстве или тестировщиком).
- В PR заполнен раздел «Использование ИИ».
- Автор может объяснить, как работает его изменение.

## Как ставить задачу

Пользуйтесь шаблоном `.github/ISSUE_TEMPLATE/task.md`. Хорошая задача:

> **Экран редактирования карточки** (этап 4, ответственный — Карпенко А., 20.10–26.10)
> Поля «лицевая сторона», «обратная сторона», «пример» (необязательно), панель башкирских букв над клавиатурой. Сохранение в базу, отмена без сохранения.
> **Готово, если:** в сборке можно создать карточку с буквами ә и ҡ, после перезапуска она на месте; макет из Figma соблюдён.

Плохая задача: «Сделать карточки».

# CLAUDE.md — проект «Туман — Языки России»

Этот файл Claude Code читает в начале каждой сессии. Здесь — общий контекст проекта; подробности лежат в `docs/`.

## Что это за проект

Курсовой проект ИТМО (дисциплина «Введение в профессиональную деятельность» у первого курса; у руководителя — «Управление проектами»). Команда первокурсников под руководством магистранта делает MVP за 7 недель: **12 октября – 30 ноября 2026**, защита 30 ноября.

**Продукт:** Android-приложение «Туман» — карточки для изучения языков коренных народов России (в MVP — башкирский язык) с адаптивным интервальным повторением по упрощённой модели FSRS и игровыми механиками.

**Цель (из ТЗ, дословно):** Разработать Android-приложение «Туман» с готовыми наборами карточек по башкирскому языку и адаптивным интервальным повторением для людей, самостоятельно изучающих языки коренных народов России, чтобы они могли регулярно заниматься без преподавателя и закреплять слова и грамматические формы.

### Состав MVP (обязательное)
- Наборы и карточки: создать, изменить, удалить; лицевая и обратная сторона, необязательный пример; панель ввода букв башкирского алфавита (ә, ө, ү, ғ, ҡ, ң, ҙ, ҫ, һ).
- Каталог готовых наборов на сервере: не менее 3 наборов по башкирскому, всего 100+ карточек, в том числе по аффиксам; загрузка на устройство.
- Повторение: список «на сегодня» по упрощённому FSRS; оценка ответа по 4 градациям («не помню», «трудно», «хорошо», «легко»); пересчёт даты следующего показа; история ответов.
- Мотивация: дневная цель, серия дней, очки опыта (XP), не менее 5 достижений, экран прогресса.
- Ежедневные напоминания с выбором времени и отключением.
- Всё, кроме загрузки наборов, работает без интернета.

### Не входит в MVP
iOS, регистрация и синхронизация, ИИ-собеседник, озвучка, распознавание текста с фото, платные функции, уроки с разными типами упражнений, другие языки. Это направления развития — не предлагай их как задачи MVP.

### Нефункциональные требования (проверяемые)
Android 8.0 (API 26)+; запуск ≤ 4 с; переход к следующей карточке ≤ 1 с; данные переживают перезапуск; ошибки сети не роняют приложение; все башкирские буквы отображаются без замены на квадраты или «?»; алгоритм повторения — отдельный модуль, независимый от UI.

Полный текст: `docs/tz.md`. **ТЗ — договор с преподавателями.** Не меняй требования молча: если задача противоречит ТЗ, скажи об этом и предложи вынести вопрос руководителю.

## Технологии и архитектура

- Android: Kotlin 2.0, Jetpack Compose + Material 3, Navigation Compose, Koin, Room, Retrofit + Kotlinx Serialization, WorkManager. Модули Gradle: `:app` и `:core-srs` (алгоритм, чистый Kotlin).
- Сервер каталога: отдельный репозиторий `tuman-langs/tuman-langs-backend` (Kotlin + Ktor, отдаёт JSON). Наборы карточек — JSON-файлы в его папке `content/`.
- Дизайн: Figma. Задачи: доска «Туман — MVP» в организации `tuman-langs` на GitHub.

**Куда класть файлы — только по `docs/architecture.md`.** Прочитай его перед планом любой задачи с кодом. Кратко:

```
app/src/main/java/ru/itmo/tuman/
├── core/       database · network · navigation · reminders · uikit · utils   ← общее
└── features/   home · decks · catalog · review · progress · settings          ← по функции
                └── <функция>/ data · domain · ui · di
core-srs/       алгоритм FSRS, без Android
```

Главные правила: экран → ViewModel → Repository (интерфейс в `domain`) → реализация в `data`; `domain` и `core-srs` не импортируют Android; одна функция не импортирует другую, общее — в `core`; тексты — в `strings.xml`.

## Как мы работаем

Путь каждой задачи один и тот же (как в CalorAI):

```
Issue на доске («На неделю»)
   │  /start-task N
   ▼
ветка feature/N-… («В работе») ── коммиты «#N: что сделано»
   │  /finish-task
   ▼
PR в main («На ревью») ◀── /fix-review ◀── замечания ревьюера
   │  одобрено → Squash and merge
   ▼
issue закрыт, карточка «Готово»
```

| Шаг | Что делает участник | Команда Claude Code |
|---|---|---|
| Что у меня в работе | смотрит свои задачи, PR и запросы на ревью | `/my-tasks` |
| Начать | ветка по правилам, план по архитектуре, карточку → «В работе» | `/start-task <номер>` |
| Работать | маленькие шаги, коммит `#<номер>: что сделано` после каждого | — |
| Сдать | свежий main, проверки, PR по шаблону с `Closes #<номер>`, карточку → «На ревью» | `/finish-task` |
| Проверить чужой PR | ревью по чек-листу, решение принимает сам | `/review-pr <номер>` |
| Исправить по ревью | правки в той же ветке, ответы ревьюеру | `/fix-review` |
| Подготовиться к защите | объяснение своей части и контрольные вопросы | `/explain-my-work [что]` |

- У каждой задачи **ровно один ответственный**, даты начала и окончания и проверяемый результат. Правила доски — `docs/kanban-workflow.md`.
- **Зависимости между задачами** записаны в разделе «## Зависимости» каждой задачи (🚧 блокер, 🤝 договорённость, ➡️ от тебя ждут) и связями «Blocked by» на GitHub. `/start-task` и `/my-tasks` проверяют их и сразу говорят о блокерах. Если по ходу работы выяснилось, что ты ждёшь чужой результат, — скажи участнику, предложи комментарий в задачу и, если надо, связь «Blocked by».
- В `main` — только через pull request с одобрением ревьюера. Прямой push в `main` и `--force` запрещены.
- Коммиты и PR — на русском, по сути: что сделано и как проверить.
- Каждый PR содержит раздел «Использование ИИ» (шаблон в `.github/pull_request_template.md`). Это требование ИТМО, а не формальность.
- Ревьюер PR по умолчанию — руководитель, GitHub `@Mimir-tu`. Вторым ревьюером можно позвать участника того же направления.
- Карточки с доски GitHub переносятся в EduFlow скриптом руководителя раз в несколько часов. Держите статус карточки актуальным: преподаватели видят его в EduFlow.

### Проверка перед PR
**GitHub Actions в этом репозитории отключены** — автоматических проверок на GitHub нет. Поэтому проверки запускаются локально, и `/finish-task` делает это всегда:
- `./gradlew test` — юнит-тесты (на Windows: `.\gradlew.bat test`);
- `./gradlew assembleDebug` — сборка APK.

Не добавляй в репозиторий файлы `.github/workflows/`: Actions выключены, такие файлы не будут работать.

Версии библиотек в `gradle/libs.versions.toml` подобраны под Android Gradle Plugin 8.13, Kotlin 2.0.21 и compileSdk 36. Не поднимай их по подсказке Android Studio без проверки: свежие AndroidX (core 1.19+, lifecycle 2.11+, activity 1.13+) требуют AGP 9.1 и compileSdk 37, и сборка ломается. KSP для Room должен совпадать с Kotlin: `2.0.21-1.0.x`.

Общие разрешения и запреты для Claude лежат в `.claude/settings.json` (например, Claude не читает `.env` и не делает `git push --force`). Личные настройки — в `.claude/settings.local.json`, он не коммитится.

## Правила для Claude в этом репозитории

1. **Объясняй, а не только пиши код.** Участники — первокурсники. По правилам ИТМО каждый обязан понимать и уметь защитить любую часть работы, включая сделанную с ИИ. На защите вопрос может прийти любому участнику про любую часть проекта. Поэтому после изменения коротко объясни, что сделано и почему, и предложи, как это проверить.
2. **Сначала план, потом код** для всего, что больше пары файлов. Покажи план и дождись согласия.
3. **Держись ТЗ и границ MVP.** Новые функции вне MVP — не реализуй, а отметь как идею.
4. **Не придумывай языковой контент.** Слова, переводы и правила башкирского языка проверяет контент-лид по словарям и учебникам. Можно помогать с форматом и структурой файлов, но не выдавать сгенерированные переводы за проверенные.
5. **Не храни секреты в репозитории.** Токены и пароли — только в переменных окружения или `.env` (он в `.gitignore`).
6. **Тесты для алгоритма обязательны.** Критерий приёмки: изменение даты следующего показа подтверждено юнит-тестами.
7. **Соблюдай архитектуру.** Новый файл — только в месте из `docs/architecture.md`. Если правка задевает зону другого участника (`docs/team.md`), скажи об этом до изменений.
8. Пиши так, чтобы код мог поддержать другой участник: понятные имена, короткие функции, комментарии там, где решение неочевидно.
